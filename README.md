# ОТЧЕТ ПО ЛАБОРАТОРНОЙ РАБОТЕ
### Тема: «Использование хранилища данных Redis в университетской системе бронирования»
**Вариант:** №1867239

**Зачинщики: Никитенко Матвей, Чайковский Никита**

**Стек:** Java, Spring Boot, Spring MVC, Spring Data Redis, Redisson, PostgreSQL, Redis  

---

## 1. Цель работы
Разработать бэкенд-компонент университетской системы бронирования (аудиторий) на базе Java Spring Boot, интегрировать документо-ориентированное хранилище **Redis** для реализации сценариев временного хранения (корзина с TTL), кэширования услуг, ограничения частоты запросов (Rate Limiter) и распределенных блокировок, а также исследовать поведение системы при потере временных ключей.

---

## 2. Архитектурный стек и обоснование выбора Redis
В системе используется гибридная архитектура хранения данных:
1. **PostgreSQL (Реляционная СУБД):** Хранит постоянные сущности (пользователи, справочник аудиторий, история заявок `Bid`, связи `BidHandler`).
2. **Redis (In-Memory Key-Value Storage):** Используется как высокоскоростной слой для работы с временными состояниями, кэшем, распределенными блокировками и ограничениями, благодаря поддержке атомарных операций (`INCR`, `EXPIRE`) и встроенному механизму TTL.

---

## 3. Модель данных и структура ключей Redis

Для реализации сценариев приложения разработана следующая схема именования ключей (Key Space):

| Тип ключа / Шаблон | Структура в Redis | TTL | Назначение |
| :--- | :--- | :--- | :--- |
| **Временная корзина** | `cart:bid:<id>` | 5 минут (300с) | Удержание заявки в статусе `PENDING` до решения администратора |
| **Статус заявки** | `status:bid:<id>` | Постоянный | Хранение финализированного решения (`APPROVED` / `REJECTED`) |
| **Занятость слота** | `booked:classroom:<id>:slot:<id>` | Постоянный | Фиксация успешного бронирования аудитории на конкретный слот |
| **Распределенный лок** | `lock:classroom:<id>:slot:<id>` | До 5 секунд | Защита от Race Condition при одновременной отправке заявок |
| **Rate Limiter** | `rate:limit:<ip>` | 1 минута (60с) | Подсчет количества запросов с одного IP-адреса |

---

## 4. Реализация дополнительных параметров варианта

### 4.1. Временная корзина и сценарий потери ключей (TTL Expiration)
* При создании заявки (`createBooking`) в Redis записывается ключ `cart:bid:<id>` со значением `PENDING` и временем жизни **5 минут**.
* **Исследование поведения при истечении TTL:** Если администратор не принимает заявку в течение 5 минут, Redis автоматически удаляет ключ `cart:bid:<id>`. При запросе статуса метод `getBidStatusFromRedis()` проверяет наличие постоянного статуса и ключа корзины. Если оба отсутствуют, система автоматически интерпретирует состояние как **`EXPIRED` (Истёк срок удержания)**. Слот при этом не блокируется, предотвращая появление «зависших броней».

### 4.2. Кэширование списка услуг (доступных слотов)
* Реализовано с использованием стандартного механизма Spring Cache (`@Cacheable("available_slots")`).
* При изменении статуса заявки администратором срабатывает `@CacheEvict(value = {"available_slots", "all_bookings"}, allEntries = true)`, что гарантирует актуальность выдаваемых свободных слотов аудиторий.

### 4.3. Атомарный механизм: Rate Limiter для REST API
* Реализован на базе перехватчика `RateLimitInterceptor` и атомарной операции `redisTemplate.opsForValue().increment(key)`.
* Ограничивает частоту запросов до **10 запросов в минуту** с одного IP-адреса. При превышении лимита возвращает HTTP-статус `429 Too Many Requests`.

## 6. Выводы
В ходе выполнения лабораторной работы было разработано полнофункциональное веб-приложение университетского бронирования. На практике доказана высокая эффективность **Redis** в решении специфических задач:
1. Механизм **TTL** позволил автоматизировать очистку просроченных корзин без написания фоновых задач (Cron-джоб).
2. Распределенные блокировки **Redisson (`RLock`)** успешно справились с предотвращением конфликтов (Race Condition) при высокой конкуренции пользователей за дефицитные временные слоты.
3. Интеграция **Rate Limiter** защитила REST API от избыточной нагрузки.

Redis продемонстрировал себя как идеальное дополнение к реляционной СУБД для управления временными состояниями, кэшем и синхронизацией в распределенных средах.
